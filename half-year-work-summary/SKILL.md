# Git 提交 → 工作总结与飞书 KPI

## 目标

将一个工作区中多个 Git 项目的指定周期提交，整理为可用于述职、绩效或半年总结的工作成果，并在需要时创建或迭代飞书文档。报告以业务交付、协同、质量和知识沉淀为主；提交数、代码行数只作为内部取证，不作为正文主叙事。

## 适用场景

- 用户说“总结我上半年/本季度/全年提交”“根据 Git 写述职或绩效总结”。
- 用户提供 KPI 截图、表格或明确考核维度，需要按模板填写完成情况。
- 用户要求把总结写入、更新或润色飞书私人空间文档。
- 用户要求把提交记录转成以工作内容、成果和业务价值为核心的报告。

## 触发方式

仅允许用户显式调用：`/half-year-work-summary`。不得因用户提及“半年总结”“绩效总结”“KPI”或飞书文档而自动加载或调用本技能。

不用于单个 PR 总结、代码审查或仅统计 Git 提交数。

## 输入

### 必需

1. **周期**：默认按自然半年或季度；未说明年份时，先根据当前日期和用户语境确认。
2. **工作区路径**：包含一个或多个 Git 项目的父目录。若用户未提供路径，且当前对话或运行上下文没有明确、可靠的项目目录，先主动询问：“需要扫描哪个工作区？请提供包含 Git 项目的项目目录路径。”收到路径前，不得扫描 `~`、当前目录或其他猜测目录。
### 可选

- 提交身份：优先读取 Git 全局 `user.name` / `user.email`，必要时识别同邮箱的 author name 别名。
- KPI 模板：截图、表格、文字指标或飞书文档链接。
- 输出位置：聊天、现有飞书文档、飞书私人空间新文档。
- 用户补充事实：日报、项目排期、线上故障、投诉、AI 使用时长、资源成本等 Git 无法证明的数据。

## 核心原则

1. **先取证，后成文。** 先确认仓库范围、提交身份、统计周期和可达提交；不要从目录名称或记忆推断工作内容。
2. **工作内容优先。** 将提交归纳为业务流、跨系统交付、质量治理和工程沉淀。不要把“提交 N 次”或“改了 N 行”放在 KPI 完成情况的主句。
3. **证据边界清晰。** Git 可以证明提交、代码变更、文档、分支合并和部分修复主题；不能单独证明工时、日报、按时提测、线上故障等级、投诉、AI 时长或资源成本。对后者标注“需补充业务系统数据”，除非用户明确提供。
4. **保留已确认内容。** 用户只要求改表格格式或某一列时，只改目标 block/列；不得用新的猜测覆盖用户已认可的完成情况。
5. **飞书文档按需处理。** 创建或编辑飞书文档前，读取并遵循 `lark-doc` 与 `lark-shared` 的技能要求；默认使用用户身份和 XML 格式。

## 执行流程

### 1. 确认范围与身份

0. 先确认工作区路径。若路径未知，先询问：“需要扫描哪个工作区？请提供包含 Git 项目的项目目录路径。”；不要通过扫描 Home 目录、当前目录或常见目录名来猜测范围。只有用户明确指定当前目录或给出可解析的路径时，才开始扫描。
1. 读取工作区第一层目录，递归核验 Git repository root，避免漏掉嵌套项目。
2. 读取 `git config --global user.name` 和 `user.email`；按 email 归集提交，再检查同邮箱是否存在 author name 别名。
3. 明确日期边界。自然半年使用 1 月 1 日至 6 月 30 日或 7 月 1 日至 12 月 31 日，时区使用本地工作时区。
4. 排除 Git stash；统计 branches、remotes 和 tags 中可达的提交。不要把 stash、未提交工作区变更或生成文件当作已交付成果。

### 2. 收集并归类证据

1. 按项目提取提交主题、日期、变更文件、merge 信息和必要的统计数据。
2. 将提交主题按业务流归并，而非按仓库机械罗列。常见分类：活动/商业化、内容分发、流程与后台、跨端能力、稳定性治理、工程化沉淀。
3. 对重要主题查看具体提交和变更文件，确认其真实边界；不要仅凭 `feat` / `fix` 前缀扩大结论。
4. 识别文档、技术方案、测试、验收、安全、性能、并发、兼容性和复用相关证据。
5. 建立“指标 → 可核验事实 → 待补数据”映射。参考 `references/evidence-matrix.md`。

#### 可复用采集脚本

优先运行 `scripts/collect_git_contributions.py` 生成 JSON 取证文件，再从项目主题和具体变更中归纳工作流：

```bash
python3 scripts/collect_git_contributions.py \
  --workspace ~/Workspace/douyu \
  --since '2026-01-01 00:00:00 +0800' \
  --until '2026-06-30 23:59:59 +0800' \
  --format json \
  --output ./git-evidence-2026-h1.json
```

脚本自动读取全局 Git `user.email`；需要统计其他身份时显式传入 `--author-email`。默认输出项目汇总和最近主题；仅在需要逐条审计时使用 `--include-commits`。

### 3. 撰写工作内容导向总结

1. 先写一段总述：职责范围、主要业务方向、工作方法和交付特点。
2. 提炼 4—6 个重点工作流。每个工作流写清：业务目标、覆盖的系统/端、完成的关键能力、解决的风险或价值。
3. 使用“完成了什么、解决了什么、带来了什么”的表达；避免堆砌仓库名、commit hash、提交数量和代码行数。
4. 将统计数据放入“取证口径”或附录，仅在用户明确要求时展示。
5. 在质量、成本、AI 效率等维度保持谨慎：没有监控、缺陷或成本数据时，描述已实施的工程动作，并列出需要补齐的数据来源。

### 4. 生成或更新 KPI 表格

用户给出类似绩效截图时，使用五列结构：

| 考核维度 | 权重 | 考核项目及目标值 | 衡量标准/关键举措 | 完成情况 |
|---|---:|---|---|---|

1. “衡量标准/关键举措”严格沿用用户给定模板，除非用户要求调整。
2. “完成情况”以工作内容和成果为核心。每格建议用 2—3 个短段落：**工作主题。**、**解决的问题。**、**沉淀/价值。**；不要退化为单句“已完成”。
3. 适度使用加粗引导词和短段落，提升可读性；不要将每格写成冗长项目清单。
4. 合并同一考核维度下的单元格，如“效率提升”覆盖研发效率、协同效率、知识沉淀；“质量保障”覆盖交付质量、质量提升。
5. 新增或修改表格时，保留用户此前确认的“完成情况”语义。格式调整不应重写已确认的工作内容。

五列表格 XML 骨架与写作示例见 `references/kpi-five-column-template.md`。

### 5. 写入飞书文档

1. 新建文档：使用 `lark-cli docs +create --as user --parent-position my_library`，将报告写入用户私人空间。
2. 编辑已有文档：先用 `docs +fetch --scope outline --detail with-ids` 定位章节；再用 `section` 或 `range` 读取目标 block。
3. 仅更新一个表格或章节时，使用 `block_replace` / `block_insert_after`；不要为了修改一列而 `overwrite` 整篇文档。
4. 只有用户明确要求整体改写，或文档由本次工作刚创建且无需保留资源/评论时，才使用 `overwrite`。
5. 写入后使用 `docs +fetch` 按 outline 和关键词核验标题、表头、重点工作流和被修改的内容；清理临时 XML 文件。

### 6. 交付

向用户提供：

- 已归纳的重点工作流与 KPI 结论；
- 证据边界和需补充的数据项；
- 飞书文档链接（如已写入）；
- 已完成的核验动作。

## 常见修正

- **“KPI 太像 Git 统计。”** 删除或下沉提交量，改写为业务交付、风险治理、协同闭环和沉淀价值。
- **“表格太单调。”** 保留模板列结构，在“完成情况”中加入加粗引导句和两到三个结果段落；不要改动已批准的事实。
- **“完成情况被改掉了。”** 从上一版文档读取用户认可的完成情况，恢复语义后再单独调整表格样式。
- **“遗漏某个项目。”** 回到项目提交主题与变更文件，增加一个明确的工作流或在对应 KPI 的完成情况中补充，不要只在统计附录加项目名。

## 输出检查

- [ ] 统计周期、身份和仓库范围明确。
- [ ] 每项重要结论都有 Git 或用户提供事实支撑。
- [ ] KPI 完成情况以工作内容为主，不以提交数为主。
- [ ] Git 无法证明的指标已标注待补数据，未被虚报为达标。
- [ ] KPI 表格与用户模板的列结构、合并关系和标准列一致。
- [ ] 用户已确认的完成情况未因排版调整被覆盖。
- [ ] 飞书文档已通过 fetch 核验，且已返回链接。
